# RSSP Group 1 — Implementation Documentation

## Research Question

> *"How do different forms of clarification questions affect a VLM-based observer's ability to understand human intent over a sequence of observed actions, as measured by information gain?"*

Everything in this codebase exists to measure this. The system observes a human cooking session clip by clip, maintains a probability distribution over candidate recipes, and asks clarification questions. The primary metric is **IG_Q** — the information gain caused specifically by a clarification question and answer, compared to **IG_obs** — the information gain from passive observation alone.

## Data Format

### Recipe scenes (`data/italian_recipe_scenes.json`)

25 Italian pasta recipes, each as an ordered list of scene sentences. Sentence format:

```
verb + object + context (present tense, no subject, no quantities)
```

Example:
```json
{
  "dish": "carbonara",
  "scenes": [
    "pours water into a large pot",
    "cracks eggs into a mixing bowl",
    "grates pecorino into the mixing bowl",
    "dices pancetta on a cutting board",
    "cooks pancetta in a skillet",
    "drops pasta into salted boiling water",
    "drains pasta over the sink",
    "transfers pasta into the skillet",
    "pours the egg mixture over the pasta",
    "stirs the pasta in the skillet"
  ]
}
```

Recipes were chosen to share many early scenes (all start with "pours water into a large pot", most include garlic, olive oil, pasta boiling) while diverging in middle and late scenes based on distinctive ingredients (eggs + pancetta for carbonara, pesto for pesto pasta, cream for alfredo etc).

### Recipe sequences (`data/recipe_sequences.json`)

Generated by `recipe_sequencer.py`. Maps each dish to an ordered list of 768-dimensional vectors:

```json
{
  "carbonara": [
    [0.12, -0.34, 0.91, ...],   ← embed("pours water into a large pot")
    [0.45, 0.23, -0.11, ...],   ← embed("cracks eggs into a mixing bowl")
    ...
  ]
}
```

Order is preserved. First vector = first scene sentence.

## Component Documentation

---

### `observation_pipeline/embedder.py`

**Purpose:** Convert any text sentence into a 768-dimensional numpy vector. Shared by both the recipe pipeline and the observation pipeline.

**Model:** `all-mpnet-base-v2` from sentence-transformers (Reimers & Gurevych, 2019). Chosen for strong semantic similarity between related cooking phrases — handles synonyms naturally (e.g. "capsicum" ≈ "bell pepper", "slice" ≈ "cut").

**Caching:** All embeddings cached to `data/embedding_cache.json`. Same sentence never embedded twice across sessions. On a warm cache, embedding is instant.

**Key methods:**
```python
embedder.embed("slices garlic on a cutting board")   # → np.ndarray (768,)
embedder.embed_batch(["slice", "chop", "boil"])       # → list of np.ndarray
```

---

### `observation_pipeline/dynamic_scene.py`

**Purpose:** Manage the growing observation sequence for one cooking session.

Each video clip produces one scene sentence (from the VLM). That sentence is embedded and appended to an ordered list. Clarification answers are also embedded and appended as special entries at their temporal position.

**Key design:** Both clips and answers are treated as elements of the same sequence. This means the observation sequence captures the full temporal context of the session — what was seen and what was asked/answered, in order.

```python
scene = DynamicScene()
scene.add("cracks eggs into a mixing bowl")       # from VLM clip
scene.add_answer("I am adding pancetta")          # from human answer
seq = scene.get_sequence()                        # list of np.ndarray
```

**Internal state:**
- `_sequence` — list of numpy vectors in order
- `_sentences` — list of dicts with `{index, type, sentence}` for each entry

---

### `recipe_pipeline/recipe_sequencer.py`

**Purpose:** One-time preprocessing step. Reads `data/italian_recipe_scenes.json`, embeds each scene sentence, saves the result to `data/recipe_sequences.json`.

**Process:**
1. Load all 25 recipes with their scene lists
2. Collect all unique sentences across all recipes
3. Embed them in one batch (efficient — no redundant embedding)
4. Build per-recipe ordered vector lists
5. Save to JSON

Run once before any experiments. Results are reused every session via the cache.

### `probability/similarity.py`

**Purpose:** Compute how well an observation sequence matches a recipe sequence.

**Why not a simpler approach:**

Several approaches were tried and abandoned:

- *Whole-recipe embeddings*: embedding the full recipe as one text string collapsed all recipes into a tight cluster — cosine similarities all around 0.94-0.96, no discrimination possible.
- *Unidirectional soft matching*: matching each observed term to its best recipe match was too generous — every recipe could match "pours water" perfectly, so short recipes with generic scenes dominated.
- *DTW (Dynamic Time Warping)*: penalised long recipes for having scenes not yet reached, amplified noise from generic early scenes, produced negative IG values.

**The hybrid approach — two components:**

**Component 1: F1 bidirectional scene matching**

Inspired by the F1 metric in information retrieval.

*Precision* — for each observed scene, find its best cosine match in the recipe:
```
precision = mean(max_cosine(obs_i, recipe_j) for each obs_i)
```
Measures: does what I've observed belong in this recipe?

*Recall* — for each recipe scene, find its best cosine match in observations:
```
recall = mean(max_cosine(recipe_j, obs_i) for each recipe_j)
```
Measures: how much of the recipe has been covered by what I've seen?

*F1* — harmonic mean of precision and recall:
```
F1 = 2 × precision × recall / (precision + recall)
```

This penalises both false positives (observed ingredients not in recipe) and false negatives (recipe ingredients not yet observed). Short recipes with generic scenes no longer dominate because their unmatched scenes reduce recall.

**Component 2: Order consistency bonus**

After F1 matching, check whether the best-matched pairs appear in the same relative order in both sequences — i.e. whether the observation forms a valid subsequence of the recipe.

A pair (obs_i, recipe_j) and (obs_k, recipe_l) is order-consistent if:
```
i < k implies j ≤ l
```

The fraction of consistent pairs gives an order_ratio in [0, 1]. This is added as a small bonus multiplier:

```
hybrid_sim = F1 × (1 + alpha × order_ratio)
```

With alpha=0.3, the maximum bonus is 30% on top of the F1 score. This rewards recipes whose scene order matches the observation order without making order the primary signal.

**Threshold:** Cosine similarities below 0.3 do not count as matches. This prevents weak semantic associations from inflating scores.

**Key function:**
```python
from probability.similarity import hybrid_similarity
sim = hybrid_similarity(obs_sequence, recipe_sequence)  # float in [0, ~1.3]
```

### `probability/belief_updater_v3.py`

**Purpose:** Maintain a probability distribution over all 25 candidate recipes. Update it after each clip and after each clarification answer. Measure entropy and IG_Q.

**Initialisation:** Uniform prior — 1/N for each recipe.

**Update mechanism:** After each observation or answer, the full distribution is recomputed from scratch using the current observation sequence. No Bayesian carry-forward. This is appropriate because the observation sequence already encodes all history — there is no information loss from recomputing.

**The update pipeline:**
```
new sentence/answer
      ↓
DynamicScene.add() or add_answer()
      ↓
hybrid_similarity(obs_seq, recipe_seq_r) for each recipe r
      ↓
contrastive_sim(r) = hybrid_sim(r) - mean(hybrid_sim over all recipes)
      ↓
softmax(contrastive_sims / T)
      ↓
updated belief distribution
      ↓
entropy() and ig_q() measured
```

**Temperature:**

Fixed at T=0.05 for all clips and answers. This is a deliberate design choice — fixing temperature ensures all IG values are computed on the same scale and are directly comparable. Temperature annealing was considered and rejected because it would make IG_obs at Clip 1 incomparable to IG_Q at Clip 3.

**Contrastive normalisation:**

Raw hybrid similarities are mean-subtracted before softmax:
```
contrastive_sim(r) = hybrid_sim(r) - mean(hybrid_sim)
```

When all recipes match an observation equally (generic scene like "pours water"), all contrastive values are near zero and the distribution stays near-uniform. When one recipe scores distinctively above average, its positive contrast drives probability mass toward it. This is grounded in information theory — the discriminative power of an observation is its relative signal, not its absolute similarity value.

**IG_Q measurement:**

Entropy is snapshotted immediately before and immediately after each clarification answer is incorporated:
```
IG_Q = H(before answer) - H(after answer)
```

This measures exactly what the answer contributed, independent of subsequent observations. The snapshot is permanent — it is not affected by later clips.

**Key methods:**
```python
updater = BeliefUpdaterV3(temperature=0.05)
updater.update("cracks eggs into a mixing bowl")     # after a clip
updater.incorporate_answer("I am using eggs")         # after human answers
updater.entropy()                                      # current entropy in bits
updater.ig_q()                                        # IG from last answer
updater.top_recipe()                                  # (name, probability)
updater.current_similarities()                        # raw hybrid sim scores
updater.current_contrastive()                         # contrastive sim scores
updater.copy()                                        # clone for EIG simulation
```

**`copy()` method:** Creates a lightweight clone sharing the embedder and recipe sequences (read-only) but with an independent observation sequence and belief state. Used by the question generator to simulate "what would happen if the human answered X" without affecting the real session.

### `probability/test_belief_v3.py`

**Purpose:** Validate the belief updater with a simulated carbonara cooking session.

**Session design:**
- 5 clips simulating a carbonara session
- 2 targeted clarification questions (after Clips 1 and 2)
- Ground truth: carbonara

**Questions chosen to maximise IG at each step:**

*Q1 after Clip 1 ("pours water"):*
> "Are you using butter, cream, or olive oil as the base of this dish?"
> Answer: "No, the fat comes from cured meat and eggs"

After one generic scene the top recipes are all butter/cream/oil based (butter parmesan, alfredo, clam pasta). A negative answer about fat source eliminates the entire top cluster in one shot. This is the highest-IG question available at this point because it targets the dominant shared feature across the top-ranked recipes.

*Q2 after Clip 2 ("cracks eggs"):*
> "Are you making a sauce based on eggs?"
> Answer: "Yes, eggs are the primary binding ingredient in my sauce"

After eggs are observed, carbonara leads. Remaining contenders are cacio e pepe (cheese-based, not egg-based) and amatriciana (pancetta-based, no eggs). Asking specifically about egg-based sauce eliminates both alternatives and confirms carbonara.

Final prediction: carbonara ✓

## Key Design Decisions and Justifications

**Why sentence embeddings over term-level IDF matching:**
IDF-based exact string matching required predefined vocabulary and broke on synonyms. Sentence embeddings handle semantic similarity naturally — "capsicum" and "bell pepper" are close in embedding space. New recipes can be added by computing their vectors without recomputing IDF across the full set.

**Why F1 bidirectional matching over DTW:**
DTW is designed for global sequence alignment and performed poorly on partial observations — it penalised longer recipes for having scenes not yet reached, causing short recipes to dominate early. F1 bidirectional matching directly captures what we need: how well does this recipe explain what's been observed, and how well does what's been observed cover this recipe.

**Why recompute rather than Bayesian carry-forward:**
The observation sequence already encodes all history. Multiplying likelihoods across steps caused numerical instability and made it difficult to cleanly attribute IG to individual steps. Recomputing from the full sequence each time produces clean, stable distributions.

**Why fixed temperature with contrastive normalisation:**
Temperature annealing was considered and rejected because it makes IG values incomparable across clips — a 0.7 bit gain at T=0.15 is not the same as a 0.7 bit gain at T=0.05. Since the research question requires direct comparison of IG_obs and IG_Q across the full session, all values must be computed on a consistent scale. Fixed temperature ensures this.

Contrastive normalisation (subtracting the mean similarity before softmax) addresses the generic observation problem in a principled way: when all recipes match an observation equally, all contrastive values are zero and the distribution stays uniform. Only when one recipe scores distinctively above average does the distribution move. This is grounded in information theory — the information content of an observation is its relative discriminative power, not its absolute similarity.

**Why observations and answers share the same sequence:**
A clarification answer is information about what's happening at a specific point in time — it belongs at its temporal position in the sequence. Treating it the same as a clip observation means the similarity computation naturally incorporates the answer's context relative to surrounding clips.

## Known Limitations

**Recipe set is finite.** The system requires recipes to be pre-represented as scene sequences. New recipes can be added by computing their vectors, but a completely unknown recipe cannot be handled. The architecture supports a large database (tested with 25, designed to scale to hundreds).

**Observation sentences must match recipe sentence style.** The VLM must produce scene descriptions in the same format as the recipe scenes (verb + object + context). Mismatch in style degrades similarity scores. In real experiments, the VLM prompt must be carefully designed to produce consistent sentence format.

**Temperature is empirically tuned.** T=0.05 was chosen by iterative testing on a single simulated session. This should be validated on real recorded sessions before final experiments. However since temperature is fixed, relative IG comparisons remain valid regardless of the absolute value chosen.

**Threshold=0.3 is empirically set.** The minimum cosine similarity threshold for counting a scene match was not derived from data. A small sweep across threshold values on real sessions is recommended.

**Early generic observations still produce some noise.** "Pours water into a large pot" is shared by all pasta recipes and should ideally produce zero IG. The contrastive normalisation reduces this but does not eliminate it entirely because recipe sequence length differences cause genuine spread in similarity scores even for generic observations. This is a data design issue — recipes of similar length and truly identical early scenes would reduce this further. Acknowledged as a known limitation.
